(2) **Cross-entity dedup check** — before returning output, read `_index/INDEX.md` plus active entity titles (✓ confirmed by explore: docs/build-pipeline/_index/INDEX.md:1-6 exists, machine-generated by `mods/workflow-index-maintainer.md` on idle hook, organized by status with |ID|Entity|Title| columns), compute lightweight similarity against the incoming directive (title tokens + first-sentence overlap + domain tag intersection), and emit a `**Dedup flag:** ⚠️ overlaps {id} ({title}) — consider {merge|link|refine}` line in Captain Context Snapshot when any active entity exceeds the similarity threshold. Both mechanisms produce text-only output into existing entity sections (✓ confirmed by explore: skills/build-brainstorm/SKILL.md:248-249 -- AskUserQuestion explicitly NOT available; existing `## Captain Context Snapshot` already carries `**Related entities**:` via Step 1b grep at SKILL.md:26-32, so dedup is a semantic upgrade of that pre-existing line); neither introduces new frontmatter fields, new primitives, or AskUserQuestion calls.

**ALTERNATIVE**: Ship dedup as a separate `/build-dedup` skill (or a pre-`/build` precheck hook), and leave brainstorm single-lens with lens-divergence deferred entirely to build-explore's contradiction pass -- D-01 rejected because (a) splitting dedup into a separate command forces the captain to remember a second step precisely when attention is focused on the new directive, and (b) deferring dual-lens to explore discards the cheapest opportunity to catch intent-vs-codebase drift -- the directive is already being parsed for domain classification, so a second lens run adds marginal cost but catches errors one pipeline stage earlier.

**GUARDRAILS**:
- Engine-freeze: no new entity frontmatter fields, no new pipeline primitives -- both mechanisms emit into existing sections (`## Captain Context Snapshot`, `## Open Questions`) as markdown text.
- Preserve the non-interactive contract: `build-brainstorm` still must NOT call AskUserQuestion. Dedup + dual-lens outputs are either informational lines or α markers that downstream stages resolve.
- Respect the "read at most 5 files for context enrichment" rule already in `SKILL.md`. Dedup query uses `_index/INDEX.md` (one file) plus fallback grep; dual-lens codebase-reality pass must cite ≤4 files. (⚠ tension: dedup 1 + dual-lens 4 = 5 already consumes the full cap, leaving zero for existing Step 1c/1d enrichment -- see Q-3)
- Dedup similarity must be deterministic (pure text analysis -- no LLM-scored embedding) so repeated runs on the same directive produce the same flag set.
- `/build` flow continues to report and commit; dedup flag does NOT block entity creation -- it informs the captain at the "Next steps" report so they can supersede/link manually.

**RATIONALE**: Dual-lens and cross-entity-dedup are sibling mitigations for the same failure mode -- brainstorm silently committing to a plausible-but-wrong spec. Dual-lens catches *intra-entity* intent-vs-reality drift (the captain's words vs what the codebase actually supports); dedup catches *inter-entity* new-vs-existing corpus drift (this directive reinventing work already planned or shipped). The two checks share machinery (directive tokenization, domain tags, `_index/INDEX.md` read) and share a failure signature (silent commit), so bundling them into one brainstorm-stage enhancement lets a single plan exercise both and keeps the quality-uplift narrative coherent alongside siblings like `stage-report-evidence-and-confidence` and `clarify-pre-presentation-evidence-gate`. The alternative single-lens-plus-later-dedup path defers both checks past the moment captain attention is maximally focused on the directive, which is when correction is cheapest.

| Option | Pros | Cons | Complexity | Recommendation |

Option A is viable if the captain accepts staleness as "idle-hook cadence is fine" and doesn't want defensive complexity. If captain picks A over C, A-3's confidence stays Unclear and the known-limitation line belongs in the skill's new Rules bullet.

## Open Questions

**Q-1**: What does the captain DO when the `consider {merge|link|refine}` line appears? Does each verb map to a concrete follow-up command or workflow, or is the verb list purely advisory prose?
- Domain: Runnable/Invokable, Readable/Textual
- Why it matters: The skill is non-interactive and produces text-only output. If the verbs have no downstream affordance, they are decorative and the captain must remember the semantics each time. If they map to commands (e.g., `/build --supersede {id}`), the brainstorm enhancement implicitly demands a `/build` flag surface that this entity does not scope.
- Suggested options:
  - (a) Advisory text only -- captain reads the flag, decides manually next session, no `/build` flag changes
  - (b) Map each verb to a specific follow-up: merge = `/build --supersede {id}`, link = add `depends-on: [{id}]` manually, refine = edit existing entity before creating new
  - (c) Drop the verb list entirely, emit only `**Dedup flag:** ⚠️ overlaps {id} ({title})` with no action hint

**Q-2**: How is "load-bearing fact" defined for the dual-lens divergence test that triggers a contradiction seed? Too loose produces Open-Question noise; too strict silently swallows divergences.
- Domain: Runnable/Invokable
- Why it matters: APPROACH says "if the two lenses diverge on a load-bearing fact" -- this is the entire trigger for the contradiction mechanism. An undefined threshold means brainstorm LLM-judges on each run, violating the "deterministic" spirit of the dedup GUARDRAIL (though that GUARDRAIL is worded only for similarity, not for divergence).
- Suggested options:
  - (a) Any named entity/system/file/protocol mentioned in one lens but not the other, OR contradicted by the other -- mechanical, may over-trigger
  - (b) Only when the codebase-reality lens cites a concrete `file:line` that refutes a captain-intent-lens claim -- requires lens citations
  - (c) LLM judgment with a 3-bullet rubric ("is this a premise the approach depends on? does the approach change if this fact is different? is this a fact about the codebase or about captain intent?") -- non-deterministic but tunable

**Q-3**: The 5-file context-enrichment cap (`skills/build-brainstorm/SKILL.md:233`) is exactly consumed by dedup (1 file) + dual-lens (≤4 files). Existing Step 1c (context-lake search) and Step 1d (git state) do not count against the file cap today, but Step 1b's workflow-dir grep does implicitly touch many files via `grep -l`. Does the cap need to be raised, scoped differently, or shared?
- Domain: Runnable/Invokable, Organizational
- Why it matters: If the cap stays at 5 and the dual-lens/dedup fully consume it, the skill can no longer read CLAUDE.md or sibling entities for brainstorm context, silently degrading brainstorm quality on scenarios where sibling context matters. If the cap is raised without scope, the skill drifts toward the explore skill's role.
- Suggested options:
  - (a) Raise cap to 8 files for the enhanced skill (dual-lens 4 + dedup 1 + context 3)
  - (b) Scope dedup reads **outside** the cap -- INDEX.md grep are "infrastructure", not "context enrichment"; dual-lens stays inside the 5-file budget
  - (c) Keep cap at 5; require dual-lens codebase-reality pass to reuse files already read in Step 1 (no net-new reads); accept that on short directives dual-lens may have 0 files to cite

**Q-4**: When `/build`'s brainstorm output includes a decomposition recommendation (parent epic + N proposed children), does dedup run on the parent directive, on each proposed child scope, on both, or is it skipped entirely for decomposed flows?
- Domain: Organizational
- Why it matters: If dedup runs on each child scope, it will very likely flag overlap with the other freshly-proposed children (they share domain tags with the parent by construction), producing noise. If it only runs on the parent, new children created in a subsequent session skip dedup entirely. Neither default is obviously right.
- Suggested options:
  - (a) Dedup runs only on parent directive; each decomposed child seeded without its own dedup pass (relies on a later `/build {child-slug}` pass to dedup)
  - (b) Dedup runs per child scope, but only flags overlaps with **existing** shipped/active entities (newly-proposed siblings in the same decomposition are excluded)
  - (c) Skip dedup entirely when decomposition is recommended -- captain triages manually
